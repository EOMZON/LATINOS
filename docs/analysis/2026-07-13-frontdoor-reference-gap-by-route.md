# Frontdoor 与最初参考稿逐模块差距清单

## 背景

本次只审计三个核心页面：

1. 首页 `/`
2. `/daily-latin`
3. `/dance-os`

唯一视觉锚点：

- `/Users/zon/Downloads/latin-workbench (2).html`

审计依据：

1. 参考 HTML 的结构与 CSS
2. 当前三个页面的 React 组件树、数据层与 CSS
3. 当前站点 1440px 桌面端真实截图
4. 既有 390px 移动端 overflow smoke 证据

这次不把“使用同一套色值和卡片语言”视为“已经一模一样”。判断重点是：模块顺序、首屏构图、信息密度、留白节奏、组件形态与内容职责是否一致。

## 问题定义

当前站已经继承参考稿的视觉基因，但三个核心页并未全部达到参考稿的页面完成度。首页是“骨架接近、下半段重组”；`/daily-latin` 与 `/dance-os` 则是“视觉语言接近，但页面构图已经变成更密集的产品工作台”。

## 优先级定义

- `P0`：直接影响“看起来是不是参考稿”的结构差距
- `P1`：影响视觉精度与页面节奏的样式差距
- `P2`：内容真实性、证据完整度或长期产品化差距
- `保留`：虽与参考稿不同，但属于合理功能升级，不应为了像而删除

## 全站共性差距

### P0：参考稿的简单层级被过多解释层包住

参考稿每页基本遵循：

`topline -> 一个主视觉/主面板 -> 一个或两个内容区 -> footer`

当前二级页普遍变成：

`topline -> anchor tabs -> intro -> summary -> bridge -> library -> interactive demo -> queue -> sources -> footer`

结果是功能更完整，但主任务不够突出，页面像内部产品说明页，不像参考稿那种一眼能扫完的个人工作台。

### P1：同一套 token，但不是像素级同款

已对齐：

1. `#0A0A0B` 背景
2. `#141416` 面板
3. `#2B2B2F` 描边
4. `#9D6FE0` 紫色强调
5. Bebas Neue / Space Mono / Noto Sans SC 字体组合
6. 232px sidebar、深色 card、pill tabs、细描边

仍不同：

1. 当前 body 额外增加全局径向渐变，参考稿只在 hero 局部有光晕
2. 当前大量模块使用更小字号、更紧间距、更低对比文本
3. 当前出现更多 16px 大圆角容器，参考稿主要是 12px / 14px
4. 当前多个 panel 再包 panel，视觉层级比参考稿更深
5. 当前 section 间距由参考稿约 56px 压到约 36px，长页更密

### P1：移动端是“可用适配”，尚非参考稿风格的移动版

当前 mobile nav 是新增的顶部折叠导航，这是合理升级；但 anchor tabs、长标签和多层卡片在 390px 下仍会形成很长的纵向路径。已有证据证明首页与 `/daily-latin` 没有横向溢出，但 `/dance-os` 还缺同等级的移动端数值与截图验收。

## 首页 `/`

### 1. Sidebar / 品牌区

状态：`P1，结构接近，内容不同`

已对齐：固定 232px、logo mark、分组导航、active 紫线、底部状态。

差距：

1. 参考稿品牌是“拉丁陪练日记”，当前是“拉丁练习入口”，品牌气质从公开成长记录变成内部入口工具
2. 参考稿导航有今日直播、训练日志、动作库、内容资产、工具、路线图、数据看板、关于；当前压缩成今日总览、旧站 Proof、Daily Latin、Dance OS 等系统路由
3. 当前底部状态文案更偏系统运维，不如参考稿直接表达“连续直播 / 今日状态”

判断：路由变化符合新 IA，应保留；但品牌名与底部状态需要重新决定是否恢复参考稿的公开叙事。

### 2. Topline

状态：`P1，形态接近`

差距：

1. 参考稿标题“今天练什么，留下什么”更像用户页面；当前“先选今天的状态，把这一轮做完”更像产品指令
2. 当前标题字重和对比更强，参考稿标题更克制、更接近说明文字
3. 当前日期 pill 加入“今天先选状态，再做一轮”，信息更长

### 3. Hero 左侧

状态：`P0，构图同款，但核心内容已改写`

已对齐：双栏比例、卡片尺寸、超大 Bebas 字、局部紫色光晕、底部三项指标。

差距：

1. 参考稿最强视觉锚点是 `42 DAY`，当前变成 `TODAY`，失去“连续成长天数”的可量化识别
2. 参考稿 hero 直接展示“伦巴 · 重心转移”；当前展示“恰恰重启 1 轮”，更像状态分流结果
3. 当前 `TODAY` 旁的小字换行紧、视觉关系弱于参考稿的 `DAY` 标记
4. 参考稿 hero 文案强调“每天练 40 分钟，把过程留下”；当前更强调先做一轮，IP 叙事弱化

建议：若目标是贴近参考稿，恢复“Day / 连续进度”为第一视觉锚点，把状态入口作为副标题或 CTA，而不是替换主锚点。

### 4. Hero 右侧

状态：`P1，最接近参考稿的模块`

已对齐：170px progress ring、下方 dashed divider、单个紫色主按钮。

差距：

1. 参考稿是 `42/100` 与今晚直播主题；当前是 `3条 今天入口`，环形进度的语义从长期进度变成入口数量，视觉与数据含义不匹配
2. 参考稿 CTA 是“进入今晚直播”，当前是“先去做恰恰这一轮”，产品逻辑正确但品牌场景改变

### 5. 连续练习热力图

状态：`P1，视觉接近但规格不同`

差距：

1. 参考稿是 100 天 / 25 列，当前是 12 周并以 4 行呈现，数据模型不同
2. 当前格子更大、更稀，参考稿更像 GitHub contribution map
3. 当前标题与注释强调入口回流，参考稿强调连续性和中断

### 6. 首页模块入口区

状态：`P0，当前与参考稿差距最大的首页模块`

参考稿：一个标题 + 6 张同等级三列卡片，直接进入日志、动作库、资产、路线图、看板、关于。

当前：外层大工作台容器 + 下一轮队列 + 独立 Demo bridge + 主入口 rail + 支持入口 rail。

差距：

1. 多了三层容器与解释文案，扫读成本明显上升
2. 模块不再同级，用户要先理解“队列 / bridge / primary / support”
3. 参考稿卡片短而完整，当前下半段在首屏截图中被截断，首页不再一屏形成完整认知
4. 当前主入口卡片信息量较多、字号偏小，失去参考稿卡片的清晰标题节奏

建议：保留队列功能，但将其压缩为一条状态 rail；模块入口恢复参考稿的 3x2 简单网格。独立 Demo bridge 不应占首页最大视觉面积。

### 7. 首页内容真实性

状态：`P2`

参考稿中的 Day 42、训练时长、资产数量本身也是示例数据；当前状态数据来自本地 witness，更真实，但长期训练天数、真实直播主题、真实内容资产总量仍未形成稳定数据源。

## `/daily-latin`

### 1. 页面定位与参考映射

状态：`P0，无一一对应参考页`

它最接近参考稿的“训练日志 + 动作库”组合，但当前把状态分流、练习闭环、回流、来源和动作库全部放在一页。视觉语言一致，页面结构不一致。

### 2. Topline + Anchor Tabs

状态：`P0`

差距：

1. 参考稿二级页 topline 后直接进入一个 detail 主面板；当前先放 7 个 anchor tabs 和 intro
2. anchor tabs 是页面目录，不是参考稿那种内容筛选 tabs；用户看到它们时尚未进入任务
3. 7 个标签在移动端会增加首屏高度和认知负担

建议：桌面端最多保留 3 个任务 tab；其余用页面自然顺序或局部 section link。移动端改成横向可滚动的短标签或下拉目录。

### 3. Daily Entry Snapshot

状态：`P1，组件语言接近 detail panel，但信息过密`

差距：

1. 参考稿 detail 是大面积媒体占位 + 右侧 5 行关键数据；当前左侧又嵌 4 个 metric 和 3 个 signal card
2. 当前右侧内容区较空，左右视觉重量不均
3. 大量 10px 左右文本在桌面截图中已接近说明书密度

建议：保留 4 个核心指标，但把 signal 收成一条“今天怎么开始”；右侧只保留定位、今天动作、做完去向三行。

### 4. 状态入口 + Daily Loop 双栏

状态：`P0`

差距：

1. 当前是两个大 panel，每个再含 3 张 card，形成明显的 card-inside-card
2. 参考稿卡片网格没有外层包裹，层级更平、更易扫
3. 六张卡同时出现，用户尚未操作就需要读大量规则

建议：合并为一个 4 步横向流程；状态只保留三个可点击入口，选中后再显示对应步骤。

### 5. Today Loop Demo

状态：`保留，但需 P1 视觉收敛`

这是当前页面真正有产品价值、参考稿没有的升级，不应删除。

差距：

1. 它目前排在大量解释模块之后，主任务到达太晚
2. Demo 内部控件、结果、witness 和历史状态同时展开，容易比参考稿工作台更复杂

建议：把 Demo 提到 snapshot 后，成为页面主模块；解释内容按需展开。

### 6. 做完后的去向 bridge

状态：`P0，重复解释`

当前 bridge cards、Daily Return Board、旧站原则都在回答“下一步去哪”，语义重叠。参考稿每页只给一个清晰下一动作。

建议：合并成一个 next-action rail，动态显示“继续 Daily / 留 witness / 进入 Dance OS”之一。

### 7. 来源矩阵

状态：`P2，适合证据层，不适合主体验层`

来源真实且符合 Feishu 规则，但公开用户不需要在核心路径里阅读产品依据。建议移到折叠“依据”或 `/about`，默认不占主页面高度。

### 8. 动作库

状态：`P1，接近参考稿但没有成为视觉主角`

已继承参考稿 pill tabs + move grid 的组件语言。

差距：

1. 在长页最底部，用户很难自然抵达
2. 参考稿动作库有明确 detail preview 与 4 列动作卡；当前 compact 模式隐藏 detail panel
3. 当前分组增加“路径”等系统信息，动作内容的纯粹性下降

建议：恢复参考稿的“选中动作详情 + 4 列库”形态，或独立成清晰子页，不要夹在闭环解释页底部。

## `/dance-os`

### 1. 页面定位与参考映射

状态：`P0，无一一对应参考页`

它借用了参考稿“工具页 + 内容资产页”的语言，但实际承担产品说明、独立 Demo 跳转、模块库、纠错、身体地图、队列和来源七种职责，是三个页面里信息架构偏离最大的一页。

状态：`P0`

差距与 `/daily-latin` 相同，但更严重：`独立 Demo / 去向 / 模块库 / 纠错 / 队列 / 依据` 是系统内部术语，不像参考稿中“动作库 / 内容资产 / 工具”那样面向普通用户。

### 3. Correction Snapshot

状态：`P1，视觉同族但主次不清`

1. 左侧 4 metrics + 3 signals，右侧 4 rows + chips，信息重复
2. `15s`、`1` 等指标缺少即时解释，不如参考稿 detail panel 的“状态 / 重点 / 问题 / 下一次”自然

### 4. 独立 Demo 入口

### 5. 去向 bridge

状态：`P0，和独立 Demo 入口重复`

独立入口已经解释 route / shell / return，随后 bridge 又解释继续 route、进入独立壳、返回 Daily。两块应合并。

### 6. Dance OS 模块库

状态：`P1，最接近参考稿内容资产页`

Hashed asset gallery 的 tabs + 网格继承参考稿 asset gallery 语言，是合理方向。

差距：

1. 参考稿资产卡是 9:13 视觉卡，有平台标签和明显封面空间；当前更像文本模块索引
2. 缺少真实动作截图、视频缩略图或身体部位图，产品主题没有视觉证据
3. “模块库”与后面的真实交互模块没有明确一一对应状态

建议：卡片使用真实 witness / 动作画面缩略图；点击后直接定位或打开对应工具。

### 7. Correction Ledger Demo

状态：`保留，P1 提升为页面主模块`

这是 Dance OS 的核心，不应排在说明和 bridge 之后。应在首个 summary 后立即出现，甚至替代 summary。

差距：当前组件功能已成立，但视觉上仍是多组表单和说明集合，缺少参考稿那种单个强焦点。

建议：每次只强调一个状态、一个身体焦点、一句 witness、一个 next step；其他历史信息折叠。

### 8. Body Map / Practice Queue

状态：`保留，但 P1 需要视觉资产`

功能是合理升级，但“Body Map”若主要以文字/格子呈现，会与名称预期不符。参考稿虽无 body map，却有明确媒体占位区；当前应至少提供可识别的人体区域图或动作帧，而不是继续叠文本卡。

### 9. 来源矩阵

状态：`P2`

对内部可信度重要，对用户主流程次要。与 `/daily-latin` 一样，应折叠或迁移到证据页。

### 10. 移动端

状态：`P0，尚缺完整验收证据`

当前 CSS 已有响应式规则，但现有正式 smoke 只写死首页和 `/daily-latin` 的 overflow 数值。`/dance-os` 包含最多 tabs、复杂 demo、queue 与 gallery，是最应该补 390px / 430px / 768px 三档截图和交互验收的页面。

## 对抗性测试

### 质疑 1：完全照参考稿会不会牺牲功能？

会。因此不应删除 Daily Loop、Correction Ledger、Queue 等核心升级。真正要复制的是参考稿的页面主次与视觉节奏，不是退回单文件 hash-tab 架构。

### 质疑 2：当前内容更多，页面变长不是正常的吗？

内容更多是正常的，但默认同时展开所有解释不正常。参考稿的优势是每页只有一个主任务。当前应通过折叠、渐进披露和独立子页控制密度。

### 质疑 3：是不是只改 CSS 就能达到“一模一样”？

不能。最大的偏差来自组件顺序和信息架构；只调色值、圆角、字号不会解决首页工作台过重、两个二级页解释层过多的问题。

## 结论

### 当前完成度判断

- 首页：视觉骨架约 `75%` 接近参考稿；主要差在 hero 数据语义与下半段工作台重组
- `/daily-latin`：视觉语言约 `60%` 接近；页面构图约 `35%` 接近
- `/dance-os`：视觉语言约 `60%` 接近；页面构图约 `25%` 接近

这些百分比是审计判断，不是像素 diff 分数。

### 唯一 Top 1

先做“三页信息层级收敛”，不要先继续微调 token：

1. 首页恢复参考稿的简单入口网格，队列压成一条 rail
2. `/daily-latin` 把 Today Loop Demo 提到首个主面板之后
3. `/dance-os` 把 Correction Ledger 提到首个主面板之后，并合并独立入口与去向 bridge

### Stop Doing

1. 不再新增解释性卡片
2. 不再用同构 detail panel 连续堆叠
3. 不把 localhost、shell、bridge 等开发语汇放进正式用户层
4. 不把“使用相同色值”当作“已经复刻参考稿”
5. 不为了视觉复刻退回单文件 HTML 或放弃现有组件化架构
