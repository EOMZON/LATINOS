# LATINOS 基础盘设计分析

## 背景

用户新开了一个空目录 `/Users/zon/Desktop/LATINOS`，希望从第一天开始就建立清晰的目录规范、agent 规则、memory 机制与长期承接结构，避免再次进入“历史项目越来越多，但边界越来越乱”的状态。

同时，用户已有旧站 `https://latindance.zondev.top/`，也已有大量旧尝试，不希望完全丢弃。新的工作既要能快速起步，也要保留旧版本与旧内容的价值。

## 问题定义

真正要解决的不是“这个空文件夹怎么摆目录”，而是：

**如何把拉丁这条长期主题组织成一个可以持续演化的母仓，同时保留旧站 proof、不破坏当前线上资产，并为新 frontdoor 与新 demo 预留清晰位置。**

## 关键约束

1. 用户不希望再次出现随意布局
2. 新内容必须优先基于 `Feishu`，不再以 `Notion` 为源
3. 旧站必须尽量保留，不宜直接覆盖
4. 新 demo、正式站、归档内容需要分层，不应混堆
5. 域名与生产入口的改动具有不可逆影响，不能在结构未稳时贸然进行

## Best Minds

### 1. Stewart Brand 视角

如果一个系统会活很久，就不该按“一次性交付物”来组织，而应该按“可演化层级”组织：

- 当前生产 proof
- 新实验
- 规则层
- 记忆层
- 迁移层

对应到当前项目，就是不要把所有内容都塞进一个网站目录。

### 2. 37signals / Basecamp 视角

如果已经有一个活着的、能工作的东西，就不要把“清理结构”和“改生产入口”绑成一个动作。

更优做法是：

- 保留旧站
- 新仓重新立规则
- 在新仓里先把下一代入口做好
- 只有在新入口真的更好时，再决定是否切主入口

### 3. 信息架构视角

用户现在最需要的不是更多页面，而是一个稳定的“工作投放协议”：

- 规则放哪
- 分析放哪
- demo 放哪
- 旧资产说明放哪
- 哪个文档是真正 source of truth

## 方案对比

### 方案 A：直接把旧站迁进新目录

优点：

- 所有东西看起来集中

缺点：

- 立即污染新母仓
- 容易误改生产站
- 新旧结构会立刻缠在一起
- 还没搞清楚 frontdoor 策略就被迫做迁移

不推荐。

### 方案 B：新目录只放规则，不放页面

优点：

- 非常稳

缺点：

- 无法尽快形成新的前台入口
- 用户仍然会觉得“结构是有了，但页面没开始”

不够好。

### 方案 C：新目录做成母仓，旧站外置保留，新 frontdoor 与 demo 在新仓并行孵化

优点：

- 结构最清楚
- 不破坏旧站
- 新入口可以快速开始
- demo 与正式站边界明确
- 未来是否切主域名可以后置决定

缺点：

- 需要明确写规则，否则未来 agent 仍可能乱放

当前最优。

## 推荐结论

`LATINOS` 应该被定义为：

**拉丁主题的母仓 / 中控仓 / 下一代 frontdoor 与 demo 孵化仓。**

不是：

- 旧站镜像
- 单一 demo 目录
- 随手实验目录

推荐目录原则：

- `docs/standards/` 放规则
- `docs/analysis/` 放决策
- `docs/legacy/` 放旧站映射
- `data/feishu/` 放来源索引
- `sites/frontdoor/` 放新前台入口
- `apps/demos/` 放新 demo

## 对抗性测试

### 失败模式 1

未来 agent 还是直接把页面、脚本、临时文件丢在根目录。

应对：

- 根级 `AGENTS.md` 强制规定目录投放协议

### 失败模式 2

有人把旧站生产代码当成“新 frontdoor”直接改。

应对：

- 在规范里把旧站路径与“默认不改”写死

### 失败模式 3

未来又开始在文档里混用 Notion 和 Feishu。

应对：

- 单独写 `source-of-truth` 规则
- 机器可读地保存飞书来源索引

### 失败模式 4

新 frontdoor 还没准备好，就先切主域名。

应对：

- 先做本地/preview
- 生产域名切换单独决策

## 结论

今天最该做的不是先搬旧文件，也不是先改域名。

最该做的是：

1. 把母仓规则立起来
2. 把 Feishu 设成唯一源
3. 把旧站与新系统的边界写清楚
4. 把新的 frontdoor 骨架搭起来
