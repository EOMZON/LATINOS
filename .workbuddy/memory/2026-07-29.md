## 完成

- **P1 判定灵敏度可调** (`04d3cce`): `judgments.ts` 加 `Sensitivity` 预设（严格/标准/宽松，默认 standard 向后兼容）；`sensitivity.ts` 管理 localStorage；`SensitivitySwitcher` 组件（顶部 HUD 常驻）；`GameScreen`+`LiveScreen` 判定传 thresholds。解决无摄像头环境无法实标阈值——标定权交还用户。
- **P2 apple-design 打磨** (`f7e996f`): `index.css` 加 `.tap` 即时按压反馈（pointer-down 0.08s scale）+ 全局 `@media (prefers-reduced-motion: reduce)` 降级（原完全缺失）；游戏 HUD 控制按钮 + `SensitivitySwitcher` 加 `.tap`。

## 关键决策
- **不伪造舞步名**：自动切段的关键动作无语义标签，硬编「纽约步/库克拉卡」会误导 → 走运动科学语言。
- **阈值标定权交还用户**：本环境无真机摄像头，不当场硬猜，做成游戏内三档可调。
- **不擅自改紫色 skin 体系**：kimi 已确认的视觉用户未要求改；打磨聚焦动效/反馈/可访问性（与配色无关）。

## 拉丁健身重构（续：从「游戏」转「健身场景」）
用户追问「效果一般,是最佳实践吗?参考健身场景实现拉丁健身构思」。微信健身文被作者隐私拦截,用户选「按最佳实践直接做」。
- **审计结论**:动作反馈引擎(髋盘/发力地图/教练)扎实,但定位是「游戏」非「健身」——缺 kcal、训练目标、健身式结算、每日打卡。
- **健身核心模型**(前序 `010e95e`/`5907f16`):`fitness.ts` 能量=MET×体重×时长,逐帧动作强度→MET(3→10);`muscleMap.ts` 编排标注作肌肉负荷来源(非肌电)。诚实约束:kcal 为估算非医学精度。
- **Chunk C 目标/体重选择器** (`0e78ebd`):ModeSelect 详情卡加目标分段控件(燃脂/塑形/律动放松)+持久化上次目标;体重 stepper(kg,localStorage);App.play 透传 goal;GameScreen 收 goal。
- **Chunk D 结算屏健身化** (`d4e8995`):主指标改🔥估算 kcal(hero)+有效时长/动作数/强度;评级降为次级「动作完成度」;肌肉负荷 Top-3 + 诚实标签「估算值·非医学精度」;「比上次」趋势(读 fitnessProgress 上一次会话);fitness.summary 加 weightKg。
- **Chunk E 每日打卡** (`8cbec80`):`fitnessProgress.ts` 按本地日期记录+连续天数(今天未练则从昨天起算)+上一次会话;TitleScreen 徽标「🔥今天还没练/✅今天已打卡·连续 N 天」。
- 验证:tsc 0 错 + `npm run build` 通过 + puppeteer-core 真 Chrome headless 验证(标题徽标/目标分段控件/体重 stepper 渲染正常,仅 favicon 404 无害)。
- 经验:多 Edit 批量改同一文件易触发 linter 竞态(useState 声明丢失),改完务必 tsc 复检;headless 验 UI 需先点「开始跳舞」而非仅靠 reload 跳过引导。
